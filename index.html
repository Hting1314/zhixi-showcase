02

它解决什么问题

每次都要重讲规则

把反复使用的处理步骤与输出要求写成 skill，也就是一类任务的执行说明，供 AI 按需读取。

记录散落，难以接着做

用本地 Markdown 文本保留任务事实，让简报、记录与看板围绕同一份资料生成。

建议太泛，结果难核对

把输出落到具体事项；日期、数字和表格交给 Python 脚本按规则处理，并保留检查环节。

03

从输入到输出，职责分开

路由负责找到任务入口；skill 提供处理规则；本地资料提供事实；AI 结合这些内容判断和表达。

04

六个核心设计点

01

规则拆成 skill

每类任务保存自己的步骤与输出要求，修改时能明确定位到对应规则。

02

显式路由，有歧义就澄清

用声明的触发词找到入口；同一片段命中多个任务时，交给上层澄清。

03

本地资料作为事实依据

事实保留在可编辑的 Markdown 中，输出与看板按需读取这些资料。

04

计算交给脚本

让 Python 按规则处理日期、数字和表格，AI 负责结合上下文判断和表达。

05

先预览，再写入

结构化操作默认 dry-run，即预览拟变更；显式指定 --apply 才执行写入。

06

输出之后还有校验

用路由用例、完整性检查与发布校验发现问题，让迭代有可核对的依据。

虚构示例 · 预设流程
1输入

“记日程：这周五整理书架，预留 30 分钟。”

虚构基准日：2026-11-02（周一）；示例日历中该日暂无安排。

2处理
  1. 匹配“记日程”，进入日程路由。
  2. 读取日程 skill 和虚构日历。
  3. 按日期规则，将“这周五”解析为 2026-11-06。
  4. 生成拟新增内容，保留写入确认。
3输出

拟新增一条日程

  • 日期：2026-11-06（周五）
  • 事项：整理书架
  • 时长：30 分钟
  • 开始时间：待补充
dry-run · 预览，尚未写入
演示只切换本页预设内容，不连接模型或读取本机资料，也不执行写入。实际系统由 AI 工具与本地规则、文件及脚本协作运行。

07

我在其中做了什么

我负责提出需求、检查结果并反馈迭代，代码主要由 AI 协作完成。

  • 定义需求从自己的日常使用中确定场景，说明要得到什么输出、哪些信息必须保留。
  • 明确规则提出任务流程、事实依据与写入边界，把模糊需求逐步变成可执行要求。
  • 核验结果检查输出是否符合事实和预期，发现错误后给出具体反馈，推动修正。
  • 持续迭代每天使用，并把实际遇到的问题带回需求与验证环节。

当前能力与项目边界

这是仅本人使用的个人系统，尚无多人使用场景的验证。

代码主要借助 Claude、Codex、Cursor 等工具协作实现；我的 Python 处于入门水平，对复杂实现仍需借助 AI 并检查结果。

AI 输出仍可能出错。系统依赖资料质量、任务规则与人工核验，测试覆盖也有边界。

08

技术栈与工具，各自承担什么

Markdown / SKILL.md
保存本地事实资料，以及按任务拆分的步骤、约束和输出要求。
JSON 路由与用例
声明触发词到任务的映射，并保存可用于回归检查的输入与预期。
Python 脚本
承担日期、数字、表格等规则处理，以及完整性检查与发布校验。
本地看板 / 定时任务
提供资料的派生视图和周期任务入口；任务声明与实际运行状态分别检查。
Claude / Codex / Cursor
用于 AI 辅助编写、修改和排查；由我提出要求、检查结果、反馈迭代。
